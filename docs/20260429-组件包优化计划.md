# MySwiftAppTools 优化计划

更新时间：2026-04-29

## 当前结论

这几天对组件包的优化方向是对的，尤其是 DesignSystem 的 `RCMTheme + RCMDesignTokens` 方案已经让组件从“硬编码样式”走向了“Token 驱动”。外部项目调用未公开 API 的问题也已经明显改善。我做了两类验证：

- 在包项目中执行 `swift build`，构建通过。
- 额外创建了一个临时外部 Swift Package，`import MySwiftAppTools` 后调用 `RCMTheme`、`RCMButton`、`RCMBadge`、`DefaultsTools`、`StoreManager`、`PermissionManager` 等入口，外部 consumer 构建通过。

目前主要问题不在“能不能用”，而在“长期维护是否干净、API 是否稳定、DesignSystem 是否足够通用”。下面是建议的后续优化计划。

## P0：清理构建警告

### 1. 移除 `RCMTheme.shared` 上多余的 `nonisolated(unsafe)`

现象：

```swift
public nonisolated(unsafe) static let shared = RCMTheme()
```

构建警告提示这个 `nonisolated(unsafe)` 对 `Sendable` 常量没有必要。

建议：

```swift
public static let shared = RCMTheme()
```

同时重新评估 `RCMTheme: @unchecked Sendable` 是否真的需要。当前 `RCMTheme.tokens` 是可变状态，如果未来允许运行时动态换肤，需要明确它只能在 `@MainActor` 配置，或者改成 actor/锁保护。

验证：

```bash
swift build
```

### 2. 清理 `ThemeManager.swift` 中无效的 `??`

现象：

```swift
var myBGColor: Color = Color.myGray ?? Color(.systemGray)
```

`Color.myGray` 已经是非 Optional，右侧永远不会执行。类似警告有多处。

建议：

```swift
var myBGColor: Color = Color.myGray
```

进一步建议：`ThemeManager.swift` 里有不少旧式样式工具，后续应该逐步迁移到新的 `DesignSystem`，避免两套主题体系长期并存。

验证：

```bash
swift build
```

### 3. 清理 `RCMDesignSystemPreview.swift` 未使用变量

现象：

```swift
case .success(let url):
    break
```

建议：

```swift
case .success:
    break
```

或者成功后给用户一个状态提示，比如保存成功的 toast。

## P1：稳定 DesignSystem 的主题架构

### 1. 明确 `RCMTheme` 的线程模型

当前 `RCMTheme.shared.tokens` 是全局可变对象，组件在 body 中直接读取：

```swift
RCMTheme.shared.colors.primary
RCMTheme.shared.spacing.md
```

优点是简单，调用成本低。风险是如果运行时切换主题，SwiftUI 不一定自动刷新，因为 `RCMTheme` 不是 `@Observable`，也不是通过 Environment 注入。

建议分两阶段处理：

第一阶段：明确约束

- 文档中写清楚：主题配置应在 App 启动时完成。
- 运行时动态切换主题暂不承诺自动刷新。
- `configure`、`applyPreset` 建议标记为 `@MainActor`。

第二阶段：支持真正动态主题

- 让 `RCMTheme` 变成 `@Observable @MainActor`。
- 提供 `Environment` 注入方式，例如：

```swift
@Environment(RCMTheme.self) private var theme
```

或提供：

```swift
.environment(RCMTheme.shared)
```

这样组件可以响应主题变化。

### 2. 统一 Theme JSON 的加载入口

当前 `Package.swift` 已经把默认主题作为资源拷贝：

```swift
.copy("DesignSystem/RCMDefaultTheme.json")
```

但 `RCMTheme.configure(jsonResource:bundle:)` 默认从 `.main` 读取。这对 App 自己的 theme 文件没问题，但读取包内默认主题时，需要调用方知道 `Bundle.module`，而外部 App 不能直接访问包内的 `Bundle.module`。

建议新增包内默认主题入口：

```swift
public func applyDefaultThemeFromPackage() throws
```

或：

```swift
public static var bundledDefault: RCMPresetTheme
```

这样调用方不用关心资源在哪个 bundle。

### 3. 减少产品名预设对通用包的侵入

当前预设里有：

```swift
.rightClickMate
.videoHero
```

这对你自己的项目很方便，但如果这个包未来给别人看，会显得业务化。

建议：

- 保留，但在文档中说明这是 MichaelDevStudio 内部预设。
- 或新增更通用命名：
  - `.orange`
  - `.purple`
  - `.blue`
- 旧名字保留为别名，避免破坏现有项目。

## P1：修正 Color 与 Codable 的健壮性

### 1. 改进 `Color.toHex()`

当前实现：

```swift
guard let components = NSColor(self).cgColor.components else { return "#000000" }
let r = Int((components[0] * 255).rounded())
let g = Int((components[1] * 255).rounded())
let b = Int((components[2] * 255).rounded())
```

风险：

- 某些系统动态色或灰度色的 components 数量可能不是 3 或 4。
- `NSColor(self)` 对某些 SwiftUI 动态色转换可能不稳定。
- 当前文件 `RCMDesignTokens.swift` 在顶部 `#if canImport(AppKit)` 引入了 AppKit，但 `toHex()` 没有用 `#if os(macOS)` 包起来。虽然包目前只支持 macOS，但未来扩平台时会成为问题。

建议：

- 显式转换到 sRGB。
- 处理 grayscale / RGB / RGBA 三类 components。
- 转换失败时抛错或返回明确 fallback。

### 2. JSON 解码建议增加容错策略

当前 `RCMColorTokens` 解码要求 JSON 中必须包含：

```swift
primary, accent, success, warning, danger
```

如果后续 token 增加字段，旧 JSON 可能无法完整覆盖新结构。

建议：

- 对颜色字段用 `decodeIfPresent`，缺失时使用默认值。
- 对 spacing/radius/typography 也考虑兼容旧 JSON。

这样外部项目使用旧主题文件时不会突然崩。

## P1：整理 Public API 边界

### 1. 为 public API 加最小化测试

目前靠手动临时 consumer 验证外部调用可用。建议把这件事固定下来。

可选方案：

- 新增一个 `Tests/MySwiftAppToolsPublicAPITests`。
- 测试里 import `MySwiftAppTools`，实例化主要 public 类型。
- 不一定测 UI 渲染，先保证 public API 不会被误改成 internal。

重点覆盖：

- `DefaultsTools`
- `KeychainTools`
- `Log`
- `ToastView`
- `StoreManager`
- `ProGatekeeper`
- `RCMTheme`
- `RCMButton`
- `RCMCard`
- `ActionBar`
- `ComponentsFlowManager`
- `PermissionManager`

### 2. 建议补一个 API 分层说明

现在包里有三类东西：

- 基础工具：`DefaultsTools`、`KeychainTools`、`FileTools`
- UI/DesignSystem：`RCMTheme`、`RCMButton`、`RCMCard`
- 历史兼容组件：`ThemeManager.swift` 中的旧样式组件

建议在 README 或单独文档里声明：

- 推荐新项目优先用 `DesignSystem/*`
- `ThemeManager.swift` 是 legacy/兼容层
- 未来计划逐步迁移旧组件到 DesignSystem

这能降低自己以后回来看时的认知成本。

## P2：DesignSystem 组件体验优化

### 1. `RCMButton` 可以增加 `LocalizedStringKey` 便捷初始化

目前 `RCMButton` 用 ViewBuilder：

```swift
RCMButton(.primary, action: {}) {
    Text("保存")
}
```

建议补充：

```swift
RCMButton("保存", role: .primary, systemImage: "checkmark") {
    save()
}
```

这样业务项目用起来更轻。

### 2. `RCMToggle` 的 label 建议支持 `LocalizedStringKey`

当前：

```swift
private let label: String
```

建议改为：

```swift
private let label: LocalizedStringKey
```

并提供 String/LocalizedStringKey 兼容初始化。这样和 `RCMPageTitle`、`RCMBadge` 更一致。

### 3. `RCMSidebarIconPresetTint` 格式和命名可以整理

当前：

```swift
case blue, green, orange, red, gray,pink,purple,teal,indigo
```

建议：

```swift
case blue
case green
case orange
case red
case gray
case pink
case purple
case teal
case indigo
```

同时考虑是否让 `.orange` 使用 `RCMTheme.shared.colors.primary` 还是 `warning`。当前 `.blue` 走 primary，`.orange` 走 warning，语义上略微混合了“颜色名”和“语义色”。

建议拆成两组更清楚：

- `RCMSidebarIconTone.primary/success/warning/danger/neutral`
- `RCMSidebarIconPresetTint.blue/purple/pink/...`

### 4. `RCMHeroPanel` 建议使用 token 里的 shadow

当前：

```swift
.shadow(color: .black.opacity(0.06), radius: 18, x: 0, y: 10)
```

既然已经有 `RCMShadowTokens`，建议统一改成：

```swift
let shadow = RCMTheme.shared.shadow
.shadow(color: shadow.shadowColor, radius: shadow.radius, x: shadow.x, y: shadow.y)
```

这样 JSON theme 才能完整控制视觉。

## P2：包结构和资源清理

### 1. 清理 `.DS_Store`

当前项目里存在多个 `.DS_Store`，包括：

```text
.DS_Store
Sources/.DS_Store
Sources/MySwiftAppTools/.DS_Store
Sources/MySwiftAppTools/Resources/.DS_Store
```

建议：

- 从 git 中删除 `.DS_Store`。
- 在 `.gitignore` 中加入：

```gitignore
.DS_Store
.build/
.swiftpm/
```

注意：如果 `.swiftpm` 中有你明确想提交的 Xcode package 配置，再单独保留需要的文件。

### 2. `DesignSystem/README.md` 是否要继续 exclude

当前 `Package.swift`：

```swift
exclude: ["DesignSystem/README.md"]
```

这是合理的，避免 README 被当资源处理。但后续如果 DesignSystem 文档越来越重要，可以考虑：

- 根 README 放总览。
- `DesignSystem/README.md` 放详细设计系统文档。
- 包资源仍然 exclude 它。

### 3. Preview 工具是否应该进入正式包

`RCMDesignSystemPreview.swift` 很有价值，但它会进入正式 library target。这样任何引用包的 App 都会编译这个预览编辑器相关代码。

建议评估：

- 如果所有 App 都可能用它，保留。
- 如果只是开发工具，考虑拆成单独 target：

```swift
.target(name: "MySwiftAppTools")
.target(name: "MySwiftAppToolsDesignPreview", dependencies: ["MySwiftAppTools"])
```

这样正式 App 可以只依赖基础工具，减少编译面和 API 面。

## P2：旧业务痕迹清理

当前还有一些历史项目名称残留：

- `TTSMate`
- `RightClickMate`
- `VideoHero`
- `DayDayUp`

这些出现在注释、预设、旧命名组件中。

建议：

- 文件头注释统一改成 `MySwiftAppTools`。
- 业务化命名组件逐步改成通用名。
- 预设可以保留，但文档明确为内部预设。

特别是：

- `VideoHeroTheme`
- `VideoHeroPrimaryButtonStyle`
- `VideoHeroGroupTitleModifier`

建议未来迁移为：

- `RCMActionTheme`
- `RCMPrimaryActionButtonStyle`
- `RCMGroupTitleModifier`

旧名字可以用 `@available(*, deprecated, renamed: "...")` 过渡。

## P3：工具类质量提升

### 1. `DateTools` 减少强制解包

当前有不少：

```swift
return date!
return diff.day!
```

建议提供安全版本：

```swift
public static func date(from string: String, format: String) -> Date?
public static func dayDifference(start: Date, end: Date) -> Int
```

旧 API 可以保留，但内部尽量改成安全实现。

### 2. `AudioPlayer` 和 `FileTools` 中的 `print` 统一接入 `Log`

当前工具类中仍有直接 `print`：

- `AudioPlay.swift`
- `FileTools.swift`
- `PermissionManager.swift`

建议：

```swift
Log.warn("...")
Log.error("...")
```

这样外部 App 可以通过 `Log.configure(isEnabled:)` 控制输出。

### 3. `PermissionManager` 的 UserDefaults 存储 key 建议可配置

当前 `DirectoryManager.key` 固定为：

```swift
AuthorizedDirectories
```

如果多个 App 或多个功能组想隔离授权目录，建议提供：

```swift
DirectoryManager.configure(keyPrefix:)
```

或让 `PermissionManager` 初始化时传入 store key。

## 建议执行顺序

1. 先清理 P0 warning，让 `swift build` 输出干净。
2. 明确 `RCMTheme` 的线程模型和运行时换肤策略。
3. 给 public API 增加最小测试，防止外部调用再次失效。
4. 整理 DesignSystem 的命名和组件便利初始化。
5. 拆分或标记 legacy：`ThemeManager.swift` 作为兼容层，不再继续扩展新能力。
6. 清理 `.DS_Store` 和历史项目名残留。

## 验证清单

每次改完建议至少跑：

```bash
swift build
```

如果改了 public API，再做一次外部 consumer 验证：

```swift
import MySwiftAppTools

let _ = RCMTheme.shared
let _ = RCMButton(.primary, action: {}) { Text("OK") }
let _ = RCMCard { Text("Card") }
let _ = DefaultsTools.shared
```

对于 UI 组件变更，建议在真实 App 中至少检查：

- 亮色/暗色模式
- 主色切换后按钮、徽章、Hero、侧边栏是否同步
- 中文/英文文案长度
- 小窗口宽度下文字是否溢出
