## 一、需求分析

### 1.1 原始需求（杨哥原话拆解）

| 编号 | 需求 | 我的理解与补充 |
|---|---|---|
| R1 | 每条消息都要保存，用 `DefaultsTools` 保存 | toast 一旦发出即落盘，App 重启后仍在。**默认记录 success / error / warning / normal，`loading` 默认排除**（可配置打开） |
| R2 | 提供消息浏览界面，Windows / macOS 消息 App 那种 | 列表式历史，顶部工具条 + 中部滚动列表 + 分页加载；每行有类型图标、消息文本、时间 |
| R3 | 按最新 → 最旧排序 | 新消息在顶部（与系统「消息 / 通知中心」一致） |
| R4 | 一屏最多 20 条，底部「更多」加载下一批 | 是「加载更多」分页（累加 20），不是翻页。不自动加载，必须点 |
| R5 | 每条消息除原有信息外，还要有时间 | 记录发出时刻 `Date`，界面按 今天 / 昨天 / 日期 分组显示 |
| R6 | 单条可删、可批量删全部 | 单条：行内 hover 删除按钮 + 右键菜单；全部：工具条「清空全部」+ 二次确认 |
| R7 | 外部 App 会调用这个界面展示和管理消息 | **关键待确认项**，见第二节。默认按「包依赖 + 嵌入视图 + 独立窗口」双形态实现，App Group 跨进程共享天然兼容 |

### 1.2 需求隐含的硬约束（不改代码就会踩坑）

1. **`ToastItem` 不能直接存。** 它含 `Image?`（不可 Codable）和 `onConfirm: (() -> Void)?`（闭包）。必须另建 `ToastRecord: Codable` 作为持久化模型，只保留可序列化字段。
2. **`ToastType` 目前没有 `rawValue`。** 需要改为 `String` 后置枚举才能存盘；升级后要做「未知值降级为 `.normal`」的解码兜底，防止未来加类型导致老数据读崩。
3. **UserDefaults 必须有条数上限。** UserDefaults 是全量 plist，启动即加载、每次写盘写整份。无上限增长会拖慢 App 启动并放大写盘开销。必须设默认上限 + 超限丢最旧。
4. **写盘时机要在主线程可控。** `show()` 是主线程调用，每次全量 JSON 编码。实测典型 30 字消息单条 211 B、500 条约 103 KB，单次编码约 1–2 ms，可接受；但如果 App 有循环刷 toast 的场景，需要提供延迟写盘开关。
5. **只限条数挡不住长消息，必须上「三重上限」。** 实测：单条 2000 字符时，500 条会膨胀到 **2.92 MB**。UserDefaults 存 3 MB 是明确的坏实践（全量 plist，启动加载 + 每次写盘重序列化）。必须同时约束「条数 + 单条长度 + 总字节」。

### 1.3 明确不做（本次范围外）

- 不做消息搜索 / 分类筛选（YAGNI，等有真实需求再加）
- 不做云同步、不做跨设备
- 不做消息「已读未读」状态
- 不做删除撤销（删除即生效，写日志留痕）

## 二、开工前必须拍板的 3 件事

### Q1「外部 app 会调用这个界面」具体指哪种形态？

这一条决定了对外 API 长什么样，必须先定。三种可能：

| 方案 | 含义 | 实现成本 | 我的判断 |
|---|---|---|---|
| **A. 嵌入视图** | 别的 App 用 Swift Package 依赖本包，把 `ToastHistoryView()` 放进自己的设置页 / Sheet | 低 | 必做 |
| **B. 独立窗口** | 提供 `ToastHistoryWindowController.shared.show()`，App 菜单项一点弹出一个独立历史窗口 | 低 | 必做（macOS 场景最顺手） |
| **C. 跨 App 共享历史** | A App 发的 toast，在 B App 的窗口里也能看到 | 中 | 靠 App Group **天然兼容**，只要两个 App `DefaultsTools.configure(appGroupID:)` 配同一个 group，历史就共享，本包零额外代码。但有硬限制：对方 App 写入后当前界面**不会实时刷新**，需 `reload()` 或重开界面（可加 Darwin Notification 做实时刷新，放二期） |

**我的建议：A + B 一起做，C 用 App Group 自动覆盖（不做实时推送，文档里写明限制）。**
如果杨哥要的是「外部 App 通过 URL Scheme 唤起主 App 的历史窗口」这种真·跨进程唤起，那是另一套方案（需要主 App 注册 scheme + 独立处理逻辑），成本高且和工具包「不写死业务 URL Scheme」的维护原则冲突，我不建议。

### Q2 历史保留上限？

| 选项 | 说明 |
|---|---|
| 200 条 | 约 70 KB，最保守 |
| **500 条（推荐）** | 实测典型消息约 103 KB，够查一周内的操作记录，UserDefaults 毫无压力；长消息由总字节上限兜底 |
| 1000 条 | 约 350 KB，仍安全但接近「该用文件/数据库」的心理线 |
| 不限制 | **强烈不建议**：UserDefaults 会被撑大，启动变慢，属于埋雷 |

超出上限按「丢最旧」处理（FIFO）。

### Q3 隐私与开关？

toast 文本里常出现**文件路径、文件名、用户输入内容**。落盘意味着这些信息进入 UserDefaults plist。

**我的建议：默认开启记录，但必须提供 `isHistoryEnabled` 总开关 + `excludedTypes` 类型过滤**，让 App 在设置里给用户一个「不记录消息历史」的选项。不额外做脱敏（脱敏规则和业务强相关，应该由调用方在 `show()` 前处理，工具包不该猜）。

## 三、技术方案设计

### 3.1 数据模型

```swift
/// 可持久化的消息记录（区别于只用于展示的 ToastItem）
public struct ToastRecord: Codable, Identifiable, Equatable, Sendable {
    public let id: UUID              // 复用 ToastItem.id，便于溯源
    public let message: String       // 落盘前按 maxMessageLength 截断（默认 500 字符）
    public let typeRaw: String       // ToastType 的 rawValue，用 String 存以向前兼容
    public let positionRaw: String   // "top" / "bottom"
    public let createdAt: Date       // 消息发出时间 ← R5

    public var type: ToastType { ToastType(rawValue: typeRaw) ?? .normal }   // 未知值降级
    public var position: ToastPosition { ToastPosition(rawValue: positionRaw) ?? .top }
}
```

设计要点：
- **用 String 存枚举而非直接存枚举**：未来新增 `ToastType` case 时，老版本 App 读到新值不会解码失败（枚举解码遇到未知 rawValue 会直接抛错）。
- `onConfirm`、`customIcon` 不落盘：闭包和 `Image` 本来也无意义，历史界面统一按 `type` 渲染系统图标。

`ToastType` 与 `ToastPosition` 需要补 `String` 原始值：

```swift
public enum ToastType: String, Codable, Sendable { case success, error, warning, loading, normal }
public enum ToastPosition: String, Codable, Sendable { case top, bottom }
```

（源兼容：现有 `switch` 与 `.success` 写法全部不受影响）

`ToastItem` 需要补一个字段：

```swift
public let createdAt: Date   // 默认 Date()，由 ToastManager.show 注入
```

### 3.2 存储层：`ToastHistoryStore`

新建文件 `Sources/MySwiftAppTools/ToastHistoryStore.swift`。

```swift
@MainActor
@Observable
public final class ToastHistoryStore {
    public static let shared = ToastHistoryStore()

    /// 新 → 旧
    public private(set) var records: [ToastRecord] = []

    public var maxCount: Int = 500                 // Q2 ✅ 已定
    public var isHistoryEnabled: Bool = true       // Q3 ✅ 已定
    public var excludedTypes: Set<ToastType> = [.loading]   // Q3/loading ✅ 已定：loading 默认不入历史
    public var maxMessageLength: Int = 500         // 单条截断（字符数），防单条超长
    public var maxTotalBytes: Int = 512 * 1024     // 总字节兜底（512 KB），防条数上限被长消息撑爆
    public var deferredPersist: Bool = false       // 高频刷 toast 的 App 打开它，合并写盘

    public func configure(maxCount:isHistoryEnabled:excludedTypes:maxMessageLength:maxTotalBytes:deferredPersist:)
    public func record(_ item: ToastItem)          // 内部：插入头部 → 截断 → 写盘
    public func delete(_ record: ToastRecord)
    public func delete(id: UUID)
    public func clearAll()
    public func reload()                           // 外部 App / App Group 场景重新读盘
    public func flush()                            // deferredPersist 模式下手动落盘
}
```

**存储细节**
- key：`"MySwiftAppTools.Toast.history.v1"`（带版本号，为将来迁移留口子；带 `MySwiftAppTools.` 前缀避免和其他 key 打架）
- 读写一律走 `DefaultsTools.shared.setCodable / codable`，因此 **App Group 配置天然生效**（这一点直接满足 Q1-C）
- 排序：写入时 `insert(at: 0)` 保持新→旧；`reload()` 时按 `createdAt` 降序再排一次，防御脏数据
- 写盘：`record/delete/clearAll` 后同步 encode + write。500 条约 1–2 ms，主线程可接受；`deferredPersist = true` 时改为标记 dirty，由 `flush()` 或退出前统一写
- **容量控制（三重上限，按顺序执行）**：
  1. **单条截断**：`message` 超过 `maxMessageLength`（500 字符）时截断并追加「…」，防单条超长
  2. **条数裁剪**：`records.count > maxCount`（500）时，从**最旧**开始丢
  3. **总字节兜底**：编码后 `data.count > maxTotalBytes`（512 KB）时，继续从最旧丢，直到降到阈值以下
  - 实测参考（500 条中文消息）：单条 30 字 → 103 KB；200 字 → 352 KB；**2000 字 → 2.92 MB（该上限已废弃）**
  - 典型使用下条数上限先生效（500 条 / 103 KB）；只有消息普遍超长时，总字节上限才会提前触发，实际保留条数少于 500——这是有意为之的取舍：宁可少留几条，也不能让 UserDefaults 膨胀到 MB 级
- 解码容错：整块解码失败（数据损坏 / 版本不兼容）时**不抛错、返回空数组并清掉坏 key**，不能让历史数据把 App 卡死

**交互规则**

  - 鼠标 hover 时行尾淡入 ✕ 按钮（沿用 `ToastRow` 的 hover 模式）

### 3.5 与现有 ToastManager 的接线

改 `ToastManager.show(...)`：构造 `ToastItem` 后，**在 append 前**调用 `ToastHistoryStore.shared.record(item)`。

```
show(text:type:...)  →  构造 ToastItem(含 createdAt)
                     →  ToastHistoryStore.shared.record(item)   ← 新增
                     →  withAnimation { toasts.append(item) }
                     →  按原逻辑定时移除
```

注意：**「被定时移除」和「被 trimToLimit 挤掉」都不影响历史记录**。历史是独立存储，两个数组生命周期互不干扰——这是这次改动的核心隔离点。

`record(_:)` 内部先做两个前置判断：`isHistoryEnabled == false` 或 `excludedTypes.contains(item.type)` 时直接 return（默认因此跳过 `.loading`），其余类型才入历史。

`ToastManager` 只加一个转发属性方便外部访问：`public var history: ToastHistoryStore { .shared }`。

3. 把本次设计的三处 API 改动临时打上去，`rm -rf .build` 后干净重建（9.46 秒，确认全量编译）→ **`Build complete!`，零错误零警告**。

### 逐项判定

| 改动 | 兼容性 | 依据 |
|---|---|---|
| `ToastType` 加 `String, Codable, Sendable` | ✅ 源兼容 | 无关联值枚举补 rawValue 不改变 `.success` 写法；**未新增 case**，外部穷举 switch 不报错 |
| `ToastPosition` 加 `String, Codable, Sendable` | ✅ 源兼容 | 同上 |
| `ToastItem` 加 `public let createdAt: Date` | ✅ 源兼容 | 实测报错 `'ToastItem' initializer is inaccessible due to 'internal' protection level` → **外部本来就构造不了 ToastItem**（memberwise init 是 internal），加字段对调用方零影响 |
| `ToastManager.show(...)` 签名 | ✅ 不变 | 参数名、顺序、默认值一概未动 |
| 新增 `ToastManager.history` 转发属性 | ✅ 纯新增 | 除非外部已有同名扩展成员（实际几乎不可能） |
| 新增 3 个 public 类型（Store / View / WindowController） | ✅ 纯新增 | 新增文件不触碰既有符号 |
| 新增本地化 key | ✅ 纯新增 | `MySwiftAppToolsL10n` 只加常量 |

### configure 相关：旧的原样不动，新的另起一个

| API | 本次改动 |
|---|---|
| `ToastManager.shared.configure(maxVisibleToasts:toastWidth:topPadding:bottomPadding:copyOnTap:)` | **一个字符都不改**：参数名、顺序、类型、默认值全部保持原样 |
| 不调 `configure` 时的默认值 | **不变**（7 / 420 / 50 / 50 / true） |
| `ToastManager.shared.show(...)` | 签名不变 |
| `ToastManager.shared.configureToastHistory(maxCount:isHistoryEnabled:excludedTypes:maxMessageLength:maxTotalBytes:deferredPersist:)` | **新增**：全部参数可选，省略即保持原值。**对外唯一的历史配置入口**（见第九节） |
| `ToastManager.toastHistory` | **新增**只读转发属性（返回 `ToastHistoryStore.shared`） |
| `ToastManager.history` | 同上，保留为旧名 |

**为什么不做成一个 configure**：展示配置（宽度/边距/可见条数/点击复制）和存储策略（上限/开关/排除类型）是两件独立的事。合并会让参数涨到 11 个，而且以后每加一个存储选项，都要去动那个所有 App 都在调的老签名。分开之后，**老 API 永远不会因为历史功能而受影响**。

也正因为分开，历史配置单独挂在 `ToastManager` 上（而不是藏在 `ToastHistoryStore` 里）——这样在 `ToastManager.shared.` 上敲点号就能发现它。详见第九节。

**老 App 不调 `configureToastHistory` 会怎样**：全部走默认值——500 条上限、开启记录、排除 `.loading`、单条 500 字符、总 512 KB、立即写盘。也就是**开箱即用、零配置**。只有想改上限、或想彻底关闭记录时，才需要写这一行：

```swift
// 可选：调整历史策略（不写就用默认值）
ToastManager.shared.configureToastHistory(maxCount: 1000)

// 可选：完全关闭历史记录
ToastManager.shared.configureToastHistory(isHistoryEnabled: false)
```

### 什么情况下才会真的破坏（本次全部规避）

1. **新增 `ToastType` case** → 外部无 `default` 的穷举 switch 立刻编译失败。本次不加 case。
2. 改动 `show()` 的参数名 / 顺序 / 默认值。本次不动。
3. 给 `ToastItem` 补 `public init` 或修改 `Equatable` 语义（现在手写的 `==` 只比 `id`）。本次不动。
4. 外部自己写过 `extension ToastType: RawRepresentable` → 与新增的 rawValue 冲突。极罕见，可接受。
5. 外部扩展 `ToastManager` 且已存在 `history` 成员 → 命名冲突。极罕见，可接受。

### 不是编译问题、但升级后必然发生的行为变化（必须在 release note 写明）

1. **老 App 一行代码不改，也会开始落盘**：`show()` 内部自动调用 `record()`。UserDefaults 会多出 `MySwiftAppTools.Toast.history.v1` 这个 key，实测典型消息约 **103 KB**（500 条），并被三重上限（500 条 / 单条 500 字符 / 总 512 KB）封顶，不会无限膨胀。老 App 无历史界面入口，属于「只写不读」的静默开销——想彻底关掉见下一条。
2. **隐私**：toast 文本常含用户文件路径，现在会进入 UserDefaults plist。若某个老 App 想保持升级前原状，加一行 `ToastManager.shared.configureToastHistory(isHistoryEnabled: false)` 即可完全关闭。
3. **App Group 场景**：老 App 若已配 App Group，历史会写进 group 容器，同 group 的其他 App 能读到。

### 版本号建议

- 打 **0.1.66** 是合适的。SwiftPM 对 `Up to Next Major from: 0.1.65` 的解释范围是 `< 0.2.0`，所以 0.1.66 会被所有老 App 自动拉取——而本次是源兼容改动，正该如此。
- **硬前提：本次绝不新增 `ToastType` case。** 一旦要加 case，就必须打 `0.2.0`，否则老 App 的穷举 switch 会炸。
- 严格按 SemVer，新增 public API 算 minor；在 0.x 区间按 SwiftPM 惯例可并入 patch，但要接受「新增 API 走 patch」的约定。若杨哥想更保守，也可以直接打 `0.2.0`，代价是老 App 不会自动升级。

## 九、补充设计（2026-09-21）：配置入口统一到 `ToastManager`

### 9.1 杨哥提出的问题

现状是两个平级写法：

```swift
ToastManager.shared.configure(maxVisibleToasts: 5, toastWidth: 420, ...)   // 展示层
ToastHistoryStore.shared.configure(maxCount: 500, isHistoryEnabled: true)  // 存储层
```

问题不在功能，在**可发现性**：调用方在 `ToastManager.shared.` 上敲点号时看不到任何历史配置入口，不查文档就不知道有这个 API。而 `ToastHistoryView` / `ToastHistoryStore` 本身也确实是 ToastManager 的范畴。

改为：

```swift
ToastManager.shared.configureToastHistory(maxCount: 500, isHistoryEnabled: true)
```

**时机极好**：`0.1.66` 尚未打 tag，`ToastHistoryStore.configure` 从未随任何版本发布过，现在调整**零兼容成本**，不必留 deprecated 别名。

### 9.2 必须避开的坑：转发不能带着默认值走

❌ **错误实现**（参数带默认值直接转发）：

```swift
public func configureToastHistory(maxCount: Int = 500, isHistoryEnabled: Bool = true) {
    ToastHistoryStore.shared.configure(maxCount: maxCount, isHistoryEnabled: isHistoryEnabled)
}
```

后果：`configureToastHistory(maxCount: 2000)` 会顺手把 `excludedTypes` 重置回 `[.loading]`、`maxMessageLength` 重置回 500、**`deferredPersist` 重置回 `false`**。后者最致命——高频刷 toast 的 App 特意打开 `deferredPersist` 是为了合并写盘，被静默改回「每条都写盘」后，性能问题极难定位。

✅ **正确实现**（可选参数，省略即保持原值）：

```swift
@MainActor
public func configureToastHistory(
    maxCount: Int? = nil,
    isHistoryEnabled: Bool? = nil,
    excludedTypes: Set<ToastType>? = nil,
    maxMessageLength: Int? = nil,
    maxTotalBytes: Int? = nil,
    deferredPersist: Bool? = nil
) {
    let history = ToastHistoryStore.shared
    history.configure(
        maxCount: maxCount ?? history.maxCount,
        isHistoryEnabled: isHistoryEnabled ?? history.isHistoryEnabled,
        excludedTypes: excludedTypes ?? history.excludedTypes,
        maxMessageLength: maxMessageLength ?? history.maxMessageLength,
        maxTotalBytes: maxTotalBytes ?? history.maxTotalBytes,
        deferredPersist: deferredPersist ?? history.deferredPersist
    )
}
```

不需要给 store 加新方法：读当前值再写回，等价于「局部更新」。全部在 `@MainActor` 上同步执行，无竞态。

**注意 `nil` 与空集的区别**：`excludedTypes: []` 是 `.some([])`，表示「清空排除列表」；不传才是「保持原样」。语义完整，没有表达力损失。

### 9.3 两层 `configure` 的语义差异（要写进文档）

| | 语义 | 适用 |
|---|---|---|
| `ToastHistoryStore.configure(...)` | **全量重置**：未传参数回落默认值 | 实例 / 测试 / Preview，需要确定性初始状态 |
| `ToastManager.configureToastHistory(...)` | **局部更新**：未传参数保持原值 | 全局单例，只改想改的那项 |

刻意保留这个差异：测试与 Preview 依赖「一次调用拿到已知状态」，改成合并语义反而要显式传满 6 个参数，噪音大。代价是同名不同语义，必须在文档里点名。

### 9.4 顺带暴露出的一个事实：实例级配置本就是伪需求

`ToastHistoryStore` 的所有实例共用**同一个 UserDefaults key**（`MySwiftAppTools.Toast.history.v1`，写死在 `persist()` 里），因此 `ToastHistoryStore()` 不是独立命名空间，只是同一份数据的另一个观察入口。

推论：外部对**自定义实例**调用 `configure` 是没有意义的——两个实例各自设不同 `maxCount` 会互相裁剪。所以真正合理的公开配置入口只有一个，就是全局那一个。

### 9.5 三条路径的处置（待定）

- **方案 A**：`ToastHistoryStore.configure` 保留 `public`，仅把文档/README 统一指向新入口。
- **方案 B（推荐）**：`ToastHistoryStore.configure` 收为 `internal`。外部只剩 `ToastManager.shared.configureToastHistory` **一条**公开配置路径，彻底杜绝两处配置打架；包内测试与 Preview 照常编译（同模块）。

推荐 B，理由是 9.4：既然实例级配置没有真实语义，就不该在外部留下第二个入口。

   - `PublicAPITests.swift`（公开 API 黑盒冒烟）**保持普通 `import` 不变**——它的职责就是证明外部能编译，改成 `@testable` 会毁掉这个作用；里面原先用 `store.configure(...)` 配自定义实例的那一段，改走 `ToastManager.shared.configureToastHistory(...)`。
2. **`internal(set)` 也需要同步**，否则外部仍可 `ToastHistoryStore.shared.isHistoryEnabled = false` 绕过新入口——这正是要堵的那条路。
